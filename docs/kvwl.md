# KVWL: workloads × models for KV-cache performance analysis

An extension of [KVC-TierSim](https://github.com/sbu-fsl/KVC-TierSim). It tests one claim:

> **The workloads and models a KV-cache paper picks change the improvement it reports.** That change can be large enough to flip which technique comes out ahead.

KVC-TierSim answers *restore or recompute?* for one request, given its hit and miss block counts. KVWL supplies those counts from real request streams, and then:

1. **Survey.** It ranks the top-50 workloads and top-50 models that recent (2024–2026) KV-cache and LLM-serving papers evaluate on.
2. **Workload dataset.** It turns each workload into a block-hashed request stream and profiles it: input and output tokens, the KV size per model, and KV reuse (prefix and non-prefix).
3. **Model catalog.** It derives per-model KV geometry (bytes/token, block bytes, sliding-window and MLA handling) and context-dependent prefill FLOPs. This replaces KVC-TierSim's single constant of 2 MB per block and 2·P FLOPs per token.
4. **Trace replay.** It replays every stream through a multi-tier (HBM→DRAM→SSD) block cache. KVC-TierSim's own policies and hardware catalog decide restore vs recompute.
5. **Analysis.** It measures how each technique's gain changes across workloads, models, load and hardware. This includes variance decomposition, rank reversals, and where "typical paper" setups fall in the population.

  data/        workload_profiles.csv  workload_model_matrix.csv  results/  analysis/  advisor/  (outputs: regenerated by the pipeline)

All paths are defined once in `datasets/kvwl/paths.py`. `kvwl.replay` imports the sibling `simulator` package (KVC-TierSim policies and hardware catalog).

## The catalog: papers, workloads, models

The three catalogs are linked by paper id (arXiv id):

```
papers.yaml                         workloads.yaml                     models.yaml
'2405.16444':                       2WikiMultihopQA:                   Mistral-7B:
  title: CacheBlend                   category: rag                      hf: mistralai/Mistral-7B-Instruct-v0.2
  venue: EuroSys'25                   hf: zai-org/LongBench              kv_heads: 8 ...
  workloads: [2WikiMultihopQA, ...]   builder: longbench                 rank: 4
  models: [..., Mistral-7B, ...]      rank: 21                           papers: ['2310.07240', '2401.18079', ...]
                                      papers: ['2311.04934', '2402.02750', ...]
```

* Workloads and models are flat maps of the same shape: **every** workload/model any surveyed paper uses is listed (87 workloads, 91 models), not only the top 50. `rank` is the survey rank by number of papers.
* `papers`, `rank` and all of `papers.yaml`/`links.csv` are generated from the survey evidence by `make catalog` (`python -m kvwl.catalog sync`); every other field is hand-curated and preserved.
* A workload with `builder: null` is surveyed but has no stream builder yet; a model with `status: pending` has no KV geometry yet. Both are skipped by the pipeline until filled in.
* A workload counted under a different survey name says so with `survey_name` (e.g. the four Mooncake traces are the survey's "Mooncake trace").
* The sweep's model list is the survey's top 50 (`survey/out/top_lists_final.yaml`); the workload list is every buildable workload.

```bash
make catalog-show NAME=GSM8K           # entry + titles of the papers that use it
make catalog-show NAME=2405.16444      # one paper
make catalog-check                     # every paper's workloads/models resolve, builders/sources exist
```

## Quick start

From the repository root (see the [top-level README](../README.md#setup)):

```bash
make venv                     # .venv with all dependencies + editable install
make fetch                    # raw sources (LongBench, L-Eval from Hugging Face; the rest from GitHub)
make fetch-hf                 # Hugging Face datasets for the `published` workloads (HF_TOKEN for gated)
make profile                  # streams + workload_profiles.csv + workload_model_matrix.csv
make profile-hf               # rebuild the `published` workloads from Hugging Face data
make sweep sensitivity        # replay sweeps (hours; JOBS=N)
make pipeline                 # analysis, advisor, atlas, explorer
```

The request streams (`<store>/streams/`, ~180 MB) and raw sources (`<store>/raw/`) are not in git and are never uploaded; they are rebuilt locally from the original sources. A rebuild from `make fetch` reproduces the shipped streams byte-for-byte (checked for LongBench, Qasper, PIQA, BBH, HumanEval).

## 1. Survey method

* **Corpus.** 273 papers with arXiv IDs from 2024–2026, taken from 11 curated LLM-systems and KV-cache paper lists and filtered to KV, cache, serving and long-context topics. On top of these come 2025–2026 venue papers found by search (OSDI'26, EuroSys'26, MLSys'26, ATC'25, and others).
* **Evidence.** A paper *uses* an item when any one of the following holds:
  * (F) its evaluation section names it. 83 papers were read in full text (24 systems papers added in round 2 to offset the compression-paper bias of code mining); see `datasets/survey/paper_evidence.yaml`.
  * (R) its artifact README names it.
  * (C) at least 2 non-vendored files in its code artifact name it.

  216 code artifacts were mined. Vendored eval harnesses (lm-eval, FastChat, OpenCompass) and LongBench's `model2path` config are excluded, as is any file naming more than 8 models (a registry).
* **Canonicalization.** `datasets/survey/dictionaries.py` holds about 80 workload and about 90 model regex aliases. Instruct, chat and context-extension variants fold into their base model.
* **Output.** `datasets/survey/out/top_workloads.csv` and `top_models.csv` give the counts per evidence type and per year. `papers.csv` gives the per-paper evidence.
* **Limitations.** arXiv full text was read for 59 papers. The rest are counted from code artifacts, which over-represents accuracy-oriented KV-compression papers relative to systems papers. That is why production traces such as Mooncake and Azure rank below 50; they are still catalogued and replayed (the catalog lists every surveyed workload, ranked). Re-running `rank.py` with more full-text entries is cheap.

## 2. Workload dataset

Each catalogued workload has a builder that reproduces *how papers replay it*: prompt template, few-shot prefix, multi-turn history, documents shared by several questions, and retrieved chunks. Each stream records its fidelity:

| fidelity | meaning |
|-|-|
| measured | real text tokenized here, or a production trace with real block hashes (Mooncake, Qwen-Bailian) |
| lengths | real token counts only (Azure, BurstGPT); no content, so no reuse information |
| published | data unreachable from the build sandbox; lengths and reuse synthesized from statistics published in the dataset paper (cited in `datasets/catalog/workloads.yaml`) |

Tokenizers: two vocabularies bundled in `mistral_common` are used. Tekken (131K, a proxy for Llama-3, Qwen, DeepSeek and GLM) and SentencePiece-v1 (32K, a proxy for Llama-2, Mistral-v0.x and OPT-era models). Each model uses its family's stream.

`datasets/data/workload_profiles.csv`, per workload × tokenizer:
* input and output tokens (mean, p50, p90, p99, max)
* sessions and turns
* `prefix_hit_ratio`: the infinite-cache share of input tokens served by an earlier block
* `nonprefix_extra_ratio`: the extra share reusable as position-independent chunks (CacheBlend/EPIC)

`datasets/data/workload_model_matrix.csv`, per workload × model:
* tokens after context truncation, and the share of requests truncated
* KV bytes/token, KV per request (mean, p99), and block bytes
* the untruncated working set
* no-cache prefill TFLOPs, and weight GB

### Model catalog verification
34 of the top-50 models were checked against their Hugging Face `config.json` (`datasets/catalog/model_verification.csv`). Fixes applied: GLM-4-9B-1M has 4 KV groups, not 2; the Qwen3 context window is 40,960; the Qwen2.5 native window is 32,768; DeepSeek-V2's window is 163,840. Gemma-7B (gated) and MPT-7B (fetch failed) are unverified. `python -m kvwl.verify_models` repeats the check when the Hub is reachable.

### Fidelity upgrades (round 2)
BBH and PIQA are now built from their real GitHub-hosted data. The published-stat estimates had been close: BBH 1.19K vs a measured 0.91K input tokens and 83% vs 84% reuse; PIQA 87% vs 80% reuse. MS MARCO joined the top 50 and is modeled as RAG with Zipf passage popularity.

The remaining synthesized workloads come from Hugging Face. `make fetch-hf` (`kvwl/hf_sources.py`) downloads and normalizes them: ShareGPT, LMSYS-Chat-1M, InfiniteBench, LongBench v2, BookSum, SCBench, LooGLE, SWE-bench agent trajectories, GPQA, HellaSwag, WinoGrande, ARC, BoolQ and COPA. `make profile-hf` then rebuilds their streams as `measured`.

The Mooncake "arXiv" trace is a near-duplicate of the tool&agent trace: identical output lengths, inputs within ±3 tokens, and 99.9% of the same unique blocks. It is excluded from aggregates.

## 3. Replay model (assumptions)

* One serving instance. GPU count is the smallest power of two that fits the weights at ≤65% of HBM (FP8 weights above 200B parameters).
* FCFS prefill queue. Prefill service = max(restore, recompute), the KVC-TierSim overlap model. Per-tier restore rates use KVC-TierSim's formulas and catalogs.
* Recompute cost includes attention over the cached prefix (context-dependent). Sliding-window and MLA layers are modeled.
* Decode iteration time = (active weights + live KV) / (HBM bandwidth × η). Live KV is pinned in HBM and shrinks the prefix cache. Admission waits when HBM is full.
* Evicted HBM blocks are written back to DRAM, and DRAM victims to SSD; write volumes are reported. Generated tokens' KV is reusable by the next turn.
* Load is a fraction of each (model, workload)'s *no-reuse capacity*: the minimum of the prefill-bound and decode-memory-bound rates. Different models are therefore compared at equal utilization. Multi-turn sessions are closed-loop with exponential think time.
* Prefill and decode do not interfere (disaggregated-style). Accuracy effects of compression and eviction are **not** modeled; only their performance side is.

Techniques (`datasets/kvwl/replay.py:TECHNIQUES`): `no_cache`, `prefix_lru/lfu/fifo` (HBM prefix cache, vLLM APC / SGLang-style), `tiered_restore` (HBM+DRAM+SSD, restore all hits; LMCache/Mooncake default), `tiered_ioaware` (+ KVC-TierSim IO-aware policy), `tiered_fp8` / `tiered_int4` (compressed stored KV), `cacheblend` (non-prefix chunk reuse with 15% selective recompute), `snapkv_2k` (2K-token decode KV budget). New techniques are a `Technique(...)` entry. Restore/recompute policies are discovered from KVC-TierSim's `simulator/core/policies/`.
